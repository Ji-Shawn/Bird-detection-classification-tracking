# 技能包提炼过程与验证边界

**技能包提炼过程：从哪些失败或观察中总结、如何验证有效、边界如何确定。**

本技能包把历史排障记录整理为另一支团队可以使用的检查方法、提示词、记录模板和报告检查脚本。提炼的结果不是一份“所有项目必须照做”的硬件口诀：同一条历史经验必须先拆成观察、解释和适用条件，再决定保留、改写或不采纳。当前技能入口为 [skill/readme.md](../skill/readme.md)，使用入口为 [skill.md](../skill/zynq_pl_accel/skill.md)。

本次整理日期为 2026-11-03。报告审查脚本的 **16 项行为测试已实际通过**；随包历史实现报告重新检查后仍为 **`review_required`，30 项待审查**。这两项结果验证了已覆盖的报告检查行为，没有重新验证历史 HLS、RTL、DMA、计时器或板卡实验。本文不把旧文中的“数百次”“全部通过”“分钟级定位”等叙述改写为本轮统计结果。

### 1.2 证据等级的使用方法

| 等级 | 定义 | 本文允许的表述 |
| --- | --- | --- |
| E0：待验证建议 | 只有新的检查方案或解释，尚无对应运行证据 | “应检查”“需要补测”，不写“已证明有效”。 |
| E1：历史叙述 | H1/H2 记载了实验和结论，本轮未获得足以复核该因果判断的完整原始材料 | “历史文档记载”，不写“本轮复现”。 |
| E2：可核对原始制品 | 可读取原始报告、日志或回执，并说明来源、对象和时间 | 可以复核其中明确记录的事实；不能扩大到未覆盖的版本、输入或环境。 |
| E3：本轮离线可重复验证 | 有本轮命令、输入身份、退出码和结果，可在对应环境再次执行 | 可报告所覆盖的软件、解析器或构建行为；必须写清是否涉及仿真、实现或硬件。 |
| E4：本轮对应对象的物理实测 | 当前待验版本与实际板卡、输入、输出和运行条件形成完整记录 | 本文的技能提炼与自检没有此项证据；不能用 E1/E2 历史材料补成 E4。 |

等级用于避免混淆来源，并非“等级越高就能证明任何事情”。例如，E3 的解析器测试不能解决 E2 报告里的 CDC 拓扑问题；带来源的历史板测日志仍然只支持其当时版本。

## 3. 关键案例：如何把一次事故变成有边界的方法

### 3.1 流水失败：先撤回错误归因，再形成验证流程

H2 同时保留了“流水化后挂起”和后来的 B2' 通过记录。这是有价值的自我纠错材料，因为它没有把失败历史删掉。但“纯计算循环可流水、流操作不可流水”仍然超出这些有限实验所能证明的范围：原文没有给出所有流循环结构、初始化方式、连续帧和反压条件的穷举证据。本文因此没有把更窄的绝对禁令当作最后答案。

还需继续追到 H4：v2 原行 253–259 曾根据 ILA 将 S2MM 永久停收解释为结构问题，但原行 260–261 明确说明这些观测发生在板状态异常期，并撤回了当时归因。本文保留“观察到停收”和“后来撤回解释”两部分，不将前者包装为本轮已经确认的 DMA 或流流水根因；其后续“边际时序”解释也仍按第 3.2 节的证据边界处理。

提炼后的任务从“把 PIPELINE 都删掉”改成“明确一次握手接受了什么、哪些状态随之推进、停顿和帧切换如何保持契约”。对应的验证设计是单帧、连续帧、随机反压和末块用例，分别记录比较数量、次序和数值。它们是后续硬件任务需要执行的方案，不是本次已经执行的实验。方法已进入 N，旧错误归因仍保留在 H1/H2 和 C §5，便于后来者看到边界如何形成。

同理，原文“失败位置随机漂移，所以不是结构性 bug”的推断也应收窄。随机现象可以提高环境、状态或输入问题的调查优先级，不能仅凭随机性排除逻辑错误。合适的结果是一个区分假设的实验，而不是立刻确定唯一根因。

### 3.2 WHS=+0.017 ns：将因果结论降回待验证假设

H2 自我纠错 4 将确定性错误归因为边际 hold，并进一步提出 0.05 ns 门槛。现有原文没有提供足以独立复核的完整配对构建、路径、约束、运行条件和控制变量记录。因此本文只保留“应调查时序及实现变化”的动机，不接受“已排除逻辑、一定由 hold 导致”的结论。

当前可读的 A1 报告给出了另一组事实：WNS=+0.128 ns、WHS=+0.005 ns，内部未约束端点为 0，但仍有 7 个 no_input_delay、11 个 no_output_delay 和 4 个 partial_input_delay；CDC 仍有 Unsafe/Unknown 项。由这些事实可以得出“摘要数值为正，覆盖与跨域仍待审查”，不能得出“硬件一定错”，也不能得出“整机已经稳健”。

这一修正已经落成可运行反例：S 中 `test_positive_small_hold_is_not_an_invented_failure` 使用人工最小摘要，确认 +0.005 ns 不会仅因旧经验阈值被判失败；`test_positive_wns_does_not_hide_missing_constraints` 确认正 WNS 不掩盖缺失输入约束。人工摘要用于验证软件判定，A1 用于说明真实待办，两者不混用。

### 3.3 ILA、cosim 与数组推断：工具结果要绑定具体对象

三类旧结论的共同问题是把某个工具结果推广到工具本身：cosim 通过就排除引擎、加 ILA 后行为变化就否定 ILA 证据、某组数组推断失败就否定所有多维数组。这些结论均不进入现行技能的自动执行规则。

可复用的方法是绑定对象。仿真结果绑定测试平台和覆盖输入；ILA 波形绑定实际下载的带探针构建、触发和运行条件；综合结果绑定具体写法、访问模式、器件和工具设置。随后用对照实验判断差异。本次没有补做这三类硬件实验，所以其工程效果仍属于 E1 的历史记载，现行交付是 T/V 中要求记录对象、条件、原始输出及反例的方法。

### 3.4 62/62、top1 和 95%：三个数字回答不同问题

“62/62”描述一组历史测试的数量及其结果；“top1=11”描述一个输入的最高分索引；“0.95”是照片记录逻辑使用的 SSD 分数门槛。这些数字不能相互替代。

H4 v3 原行 73–74 披露 L24 存在 1 字节 tie，并由当时程序作 `bad<=1` 特判；v5 原行 544 又明确 62/62 沿用包含“跳过 stem”和该舍入特例的历史判定。这类结果应表述为“按当时判据通过”，不能重新整理成“所有层都执行、所有字节零差异”。本报告没有审定该特判适用于当前所有模型，迁移时必须重新定义并验证。

例如，A2 的 [candidate_chain_1_head.txt](../board/evidence/history_models_20261002/candidate_chain_1_head.txt) 同时记录 `top1=0000000B`、`expected_top1=0000000B`，以及非零的 `visual_bad=0000047A`、`logits_bad=00000038`。可以说该历史输入 top1 一致，不能省略差异字段再宣称所有输出字节一致。日志的具体比较语义还应结合当时验证程序解释。

SSD95 则是生产规则验证：当前 37 项原生测试包含阈值边界、资格状态和文件写入相关场景，其中 5 项执行 FatFs 集成。回执明确是确定性输入且未访问物理板卡；它们不能报告鸟类识别准确率。要回答准确率，需要另行定义有标签的评估数据、统计口径和真实评估结果；本文没有这份新增实测。

### 3.5 资源异常：检查后续更正，不能停在第一份总结

H2 性能主线第 10 项保留了 339 DSP 超编和共享 MAC 池的阶段性记录。H4 v2 原行 223–226 曾把额外 DSP 归因于组合加法链；v3 原行 91–94 改为记录操作数被扩为 32 位、每个相应乘法使用两个 DSP48，并记载窄位宽共享池后为 DSP 35、LUT 23K、BRAM 50。本文以此说明归因发生过变化，不将早期解释写入最终规则。

这些资源数字仍来自交接叙述，本轮没有重新获得并运行那几套原始综合对照。704K/1037/22K LUT 的数组案例也不能因为出现在 H1 和 H2 两处就变成独立复核。可迁移的规则是先检查实际操作数位宽、访问模式和综合映射，再设计对照；“多维数组不能推断”“整字 1R1W 是唯一安全形态”均不作为通用结论。

## 4. 本轮技能自身的验证：从 15 项通过到发现漏行

### 4.1 第一轮通过并不意味着检查器没有缺陷

最初的报告检查器已有 15 项测试，包括正余量、负余量、缺报告、缺覆盖、截断、非有限值、零检查端点、资源预算、设计名混用、CDC Unsafe、退出码和真实报告等情况。独立审阅随后构造了更具体的反例：同一 CDC 表先放一行合法 Info，再附一行不支持的严重级别。

```text
Info  clk_a  clk_b  Safely Timed  None  1  1  0  0  0
Critical Warning  clk_a  clk_b  User Ignored  False Path  1  0  1  0  0
```

旧实现只选择以已知 `Critical`、`Warning`、`Info` 加连续空格开头的行。第二行的 `Critical Warning` 没有命中这个筛选条件，整行被跳过；第一行又足以满足“至少解析到一行”。于是存在问题的输入得到 `screen_pass`。这个缺陷说明，“已经有反例测试”仍不等于“所有假绿路径已覆盖”。

### 4.2 修复并验证没有改变原有真实结果

修复后的 I 先匹配完整 CDC 表头，再读取数据区域；空行和分隔线可以略过，其余行必须符合已支持的列结构、严重级别和数字格式。任何未知行均产生带行号的 `incomplete`，不再通过“只读认识的行”得到绿色结论。对未知 `Critical Warning` 返回未完成，而不是擅自映射为另一个已支持严重级别。

新增的 `test_unknown_cdc_row_after_valid_info_is_incomplete` 含三个子例：未知组合严重级别、带缩进的未知严重级别和截断数据行。三个子例均在一行合法 Info 后追加异常，检查状态为 `incomplete`、退出码为 3、CDC 指标未被当作完整结果保留，并检查有明确 CDC 错误。它是 **1 个 unittest 测试方法、3 个子例**，因此总计为 **16 项**，不把子例混算为 18 项。

独立构造的原反例也用修复后脚本重新执行，结果为 `incomplete`，退出码 3，错误为 `Unsupported CDC row at line 8`。该次临时输出仅用于现场定位；持久交付的回归入口是 S 中的上述测试，不能依赖临时目录才能重现。

随后对 A1 的五份真实历史报告重新检查，输出与 V2 的 JSON 完全一致，仍为 `review_required`、30 项 findings。这个回归证明该修复保留了已知真实样本的原有提取结果；它没有关闭这 30 项审查任务。

### 4.3 迁移到另一项目时，不把旧工程资源数当成门槛

独立审阅还指出：如果另一支团队复制技能，目标项目也有 `build/reports/`，固定样本测试不应强制新项目等于 LUT 43722、DSP 164。当前 S 会先根据 V2 记录的各报告 SHA256 识别是否是原始发布样本。缺失或身份不同则明确跳过该固定样本断言，通用人工反例继续运行；新项目的报告应另用 I 审查。

这里“跳过”不是新项目通过，也不是本项目回归通过。当前原项目的 V1 记录为 16 项、0 跳过；迁移项目若跳过固定样本，测试输出必须如实保留 skip，不能把原项目数字用于新项目宣传。

## 5. 提炼生命周期：如何让下一次反例进入技能

| 阶段 | 具体工作与产物 | 进入下一阶段的条件 |
| --- | --- | --- |
| 1. 收集 | 保存原失败输入、实际输出、命令、版本和操作者记录；原总结只作来源索引 | 能区分原始观察与作者解释；缺项先标明。 |
| 2. 拆分 | 将一句结论拆为“看到什么、怀疑什么、已经排除什么、还缺什么” | 不再用通过字样、单次 top1 或数值阈值代替因果证据。 |
| 3. 分级 | 标 E0–E4，标日期和对象；相同摘要不重复计作独立实验 | 每个声称的效果都能指到相应材料；不足的结论降级。 |
| 4. 选择 | 保留有用观察；改写可迁移方法；不采纳没有依据的普遍禁令 | 规则包含前提、成功判据、失效条件，不迁移未确认常量。 |
| 5. 最小验证 | 先跑原失败用例，再加最接近的通过例与破坏例；改变一个关键因素 | 缺文件、零比较、未知格式和错误值能按预期失败，不因放宽门槛获得通过。 |
| 6. 固化 | 简短入口放 skill.md；步骤放 references；重复机械工作进 scripts；记录结构进 assets | 新团队不依赖原开发机私有路径、未随包脚本或旧会话才能开始。 |
| 7. 独立审阅 | 让未参与实现的人按文档使用，尝试未知输入和新目录 | 实际反馈进入缺陷记录。本轮未知 CDC 行与固定样本迁移问题来自此环节。 |
| 8. 发布与再修订 | 更新测试、示例、文档和回执，保留旧误判及反例，不篡改旧实验日期 | 已知样本回归一致；新规则的边界和未覆盖项公开。发现新反例后回到第 2 阶段。 |

这种生命周期的有效性以实际缺陷闭环评价。本轮可以证明的是：独立审阅发现了一条原测试遗漏的假绿路径，修复后反例失败、已知样本不变、测试和说明同步更新。至于“节省几小时”“陌生团队必然一次成功”，目前没有对照记录或独立团队统计，不给出量化收益。

## 6. 当前交付的可复用能力与未测边界

已经可以直接使用的部分包括：以五份报告为输入的确定性摘要检查；有状态和退出码的结果 JSON；包含破坏输入的自检；数值排障检查顺序；给模型的具体任务模板；实验和告警的记录模板。这些文件不依赖安装某个智能体，普通读者也能按 [复现文档](../reproduce.md) 使用。文件保持小写英文；如果代理框架要求大写技能入口，只在仓库外的个人副本适配名称，不改变比赛包命名规则。

仍需明确保留以下边界：

1. **未知报告格式不放行。** 当前解析器主要验证随包英文 Vivado 2023.2 摘要。其他语言、版本、选项或没有 crossing 行的 CDC 摘要需要适配；`incomplete` 不能当作零问题。
2. **摘要无法证明来源完全配套。** 设计名一致和哈希稳定不等于五份报告必然来自同一 checkpoint。还需构建来源、源码、约束、bit/ELF 和实验记录配对。
3. **报告待办没有被模板关闭。** Unsafe、Unknown、I/O delay、方法学和 DRC 条目需要对象级证据；脚本没有全局忽略告警开关，也不能批准豁免。
4. **未新增旧硬件案例的复测。** 本次没有重跑 HLS、cosim、DDR/DAP 故障、计时器标定、ILA、数组综合或历史 62 项板测。相关经验保留其 E1/E2 身份。
5. **离线通过不推出整机效果。** 没有新增当前版本物理冷启动、长期稳定性、传感器融合、机械运动、物理 SD 卡时延或现场模型准确率结论。
6. **模板效果仍需按任务积累。** T/V/F 规定如何记录事实，未预置 PASS，也没有证明任何模型仅凭提示词即可稳定完成全部硬件任务。
7. **复用数字需重新定条件。** 0.05 ns、95.72 ns/tick、201 拍、62 项、某组资源数和性能预测都不能当作新项目默认验收常量。规则应复用检查方法和证据结构。

新团队提交一个后续案例时，至少附上原失败、原始材料、对象版本、唯一关键改动、复跑命令、实际结果、反例和适用边界。证据不足的案例可以进入历史观察区，但不能因为写成技能文档就自动升级为已验证规律。
