# 低 LUT 提帧率方案评估（2026-10-14）

## 结论

选择继续开发“采集流旁路计算 UDP 负载 CRC + BRAM 保存每包结果”的方案。它保持像素和协议校验不变，目标是减少 Cortex-A9 发包时重复扫描图像的耗时。本轮完成资源审计、软件对照和独立 RTL 原型验证，尚未集成整机、生成新 bit 或证明帧率提升。

资源明细见 ../m24_low_lut_crc/RESOURCE_AUDIT.md。当前整机 LUT 45903/53200，DSP 剩130，BRAM36等效剩55.5；占用Slice 13118/13300。原整机 WNS +0.089ns、WHS +0.009ns，新增逻辑必须重新整机实现。

## 已完成的实验

- M24 slicing-by-16：16432个软件正确性用例通过；板测每包CRC由约10.1–10.2us增至11.9–12.0us，弃用。
- M24b 32位加载的slicing-by-8：16432个正确性用例通过；每包CRC约11.1–11.2us，仍慢于原版约10.2–10.3us。表面FPS波动同时伴随摄像头采集速率波动，不作为优化收益，弃用。
- crc16_stream.sv：每拍接收16位、标准反射CRC32、按包结束、支持尾部单字节、复位和输出反压。XSim逐包对照Python zlib：3042包、2123546输入字、2265319周期、197次输出反压，TEST_PASS。
- 独立综合资源：138 LUT、65 FF、0 DSP、0 BRAM（见crc_utilization.rpt）。这只是CRC核，不包含整机接口、缓存、跨时钟和控制。
- 独立100MHz布局布线的内部路径WNS +4.871ns、WHS +0.253ns。OOC输入输出未约束且未指定整机时钟源，不能作为集成时序签核。

## 集成方案与验收条件

1. 在发送像素对应的采集数据流旁路计算CRC；必须与真实UDP负载的1400字节分包边界一致，不能把视频行末当作包末。
2. 通过BRAM存储每帧的CRC表，并携带帧序号、缓冲区身份、有效位；PS仅对完全匹配的帧使用结果。若裁剪、缩放、发送格式改变，需重新定义对应关系；表不匹配时回退原软件CRC。
3. 1920x1080 RGB565每帧2963包，32位CRC表11852字节。三帧共35556字节，若每帧用4096x32存储，约12个BRAM36等效块；这是缓存预算，不是已综合结果。可按实际缓冲区数量收缩。无需额外完整帧缓存或独立DMA。
4. 接口控制目标新增不超过500 LUT（含138 LUT核），只是设计预算，需整机综合证明；优先复用现有寄存器读口，避免新AXI互连。
5. 必须验证丢帧、切换缓冲、跨时钟、复位、尾包和陈旧CRC回退。整机实现时检查setup/hold、CDC和拥塞，再做同模式、同曝光、同10us发包间隔的FPS/丢包/方位/音频期限对照。

CRC按原板测约10us/包，2963包约30ms CPU时间/帧。这不是可直接相减的端到端耗时或FPS保证，DMA、网络、调度及流水重叠会影响收益。DSP空闲不能直接加速以异或为主的CRC。
